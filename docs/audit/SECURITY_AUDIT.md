## AQUA-SEC-001 — токен любого аккаунта по публичному ключу

- **Проект / приоритет / компонент:** Aquamarine, P0, Authentication.
- **Файлы:** `crates/aqua-server/src/auth.rs` (стр. 86–95, 133–148, 267), `crates/aqua-server/src/lib.rs:486` (`GET /v1/bundle/:user`), `crates/aqua-core/src/devlist.rs:148-158`, `crates/aqua-server/src/directory.rs:1717-1735`.
- **Тип:** подтверждённый баг.
- **Описание.**
  - Nonce challenge привязан только к X25519 (`dh_pub`).
  - Подпись nonce проверяется ключом `body.identity.sign_pub`, который клиент присылает в том же запросе.
  - Токен содержит только `dh_pub`.
  - Сервер нигде не связывал Ed25519 с X25519.
- **Доказательство.**
  1. Атакующий берёт `identity.dh_pub` жертвы из открытого `GET /v1/bundle/<user>`.
  2. Запрашивает `/v1/auth/challenge` с этим `dh_pub`.
  3. Подписывает nonce **своим** Ed25519 и шлёт `identity = {sign_pub: свой, dh_pub: жертвы}`.
  4. Получает токен жертвы.
  - Шаги 1–3 (без proof) закодированы в тесте `token_forgery_with_foreign_signing_key_is_refused`. На старом коде этот тест не запускался. Что запрос там проходил, следует из кода: `auth.rs:267` проверяет подпись ключом из того же запроса, а другой проверки нет.
- **Последствия.**
  - WebSocket от имени жертвы: чтение её очереди (`lib.rs:648,658`), отправка с `from = victim` (`lib.rs:778`).
  - Бэкап, смена пароля и 2FA, удаление устройств, `/v1/me/pass`.
  - Подмена `sign_pub` и prekeys в bundle. Расшифровать новые сессии атакующий не может (нужен закрытый X25519), но может сорвать их.
- **Причина:** подпись доказывала владение каким-то Ed25519, а не ключом аккаунта.
- **Исправление.**
  - Challenge выдаёт одноразовый X25519 `server_eph`.
  - Verify требует `dh_proof = HMAC-SHA256(HKDF(DH(identity_x25519, server_eph), "aqua-auth-dh-proof-v1"), nonce‖dh_pub‖sign_pub)` (`aqua_core::wire::auth::dh_proof`).
  - Неконтрибутивный (нулевой) общий секрет отвергается с обеих сторон.
  - Ed25519, доказанный при первом входе, сохраняется в `identity_signs(dh, sign)`. Другой Ed25519 для того же X25519 — 403 при входе, загрузке bundle и `put_devlist`.
  - `pending` ограничен `MAX_PENDING` = 50 000.
  - Старые токены перестают действовать после перезапуска: новый `server_key`.
  - `MIN_VERSION` = 1.21.0-23 (решение владельца).
- **Тестирование:**
  - `token_forgery_with_foreign_signing_key_is_refused`: без proof → 401; proof чужого ключа → 401; случайный proof → 401; повтор verify → 4xx; владелец входит;
  - `bundle_with_unproven_signing_key_is_refused` → 403;
  - `auth::tests::dh_proof_matches_only_with_the_identity_secret`;
  - `auth::tests::pending_is_capped`.
- **Результат:** PASS.
- **Остаточный риск.**
  - Привязка Ed25519 — TOFU на каждом сервере: первый доказанный вход фиксирует пару. До первого входа после обновления атакующий не может зафиксировать свой ключ, потому что для proof нужен закрытый X25519.
  - `put_devlist`, пришедший по федерации (`fed_apply_user`), не проверяется этим механизмом. Он закрывается моделью доверия узлов (AQUA-SEC-009).
  - CeZeOs `ecosystem.mjs` проверяет подпись издателя Aquamarine (`CEZEOS_AQUAMARINE_ISSUER`), но в коде Aquamarine такого издателя нет (`grep cezeos-link` пусто). Интеграция существует только с одной стороны — UNVERIFIED.

## AQUA-SEC-002 — пропуск `aqpass` перезаписывал ключ аккаунта

- **Файлы:** `crates/aqua-server/src/directory.rs:1458-1477` (`register_joined`), `directory.rs:2303-2378` (`fed_apply_user`), `lib.rs:1281-1304`.
- **Тип:** подтверждённый баг.
- **Описание.** `register_joined` отказывал, только если отличались и ключ, и uid. Иначе выполнялось `ON CONFLICT(username) DO UPDATE SET identity_dh=?2`. Затем `fed_apply_user` («новее — побеждает») разносил новый ключ по сети.
- **Доказательство.** Тест `solo_relay_shares_only_names` (дополнен):
  1. Пропуск @bob с сервера A.
  2. Вход на A с другим ключом.
  3. `signup` с пропуском.
  - Раньше запрос проходил и записывал чужой ключ. Теперь 4xx, ключ @bob не изменён.
- **Последствия:** захват аккаунта во всей федерации. В связке с SEC-001 пропуск можно было выпустить для чужого аккаунта.
- **Исправление:** у существующей записи `identity_dh` не перезаписывается; другой ключ получает `UsernameTaken`.
- **Результат:** PASS.
- **Остаточный риск.** Пропуск по-прежнему действует «на предъявителя» 10 минут и один раз. Так задумано: его текст переносят на другое устройство. Кража текста пропуска даёт вход на соло-сервер.

## AQUA-SEC-003 — dev-коды включены по умолчанию

- **Файлы:** `directory.rs:874-875`, `lib.rs:1101`, `directory.rs:2021-2025` (`reset_password`).

- **Сценарий захвата.**
  1. `request {purpose: reset}` → `dev_code`.
  2. `verify` → ticket.
  3. `/v1/users/reset`: если у аккаунта нет ключа восстановления, пароль меняется без других проверок.
  4. `/v1/users/login` на своём устройстве.
- **Исправление:**
  - dev-коды только при `AQUA_DEV_CODES=1`;
  - без почты код остаётся в консоли и в панели «Коды»;
  - `open_memory` по-прежнему включает dev-коды, но сам откат на память теперь только явный (SEC-004).
- **Тестирование:** `email_codes_are_hashed_single_use_and_limited` (`!dev_codes()` по умолчанию); e2e-тесты явно ставят `AQUA_DEV_CODES=1`.
- **Результат:** PASS.
- **Остаточный риск.**
  - Сброс пароля без ключа восстановления по-прежнему опирается только на почту. Это стандартная модель «забыли пароль», а не дефект.
  - `/v1/auth/email/request` раскрывает, зарегистрирован ли адрес (409/404). Перечисление адресов — P2, не исправлено.

## AQUA-SEC-005 — OTP: открытый текст, без лимитов, многоразовый

- **Файлы:** `directory.rs:601-607`, `1020-1054`.
- **Что было:**
  - код хранился открытым текстом и сравнивался `!=`;
  - после `verify_code` код не гасился;
  - число попыток не ограничивалось;
  - на request/verify не было rate limit, повторную отправку ничто не сдерживало;
  - распределение кода было смещено (`u32 % 1e6`).
- **Исправление:**
  - код хранится как HMAC(ключ, случайный при каждом старте, `email|code`) и сравнивается `subtle_eq`;
  - после успешной проверки код опустошается;
  - после `CODE_MAX_FAILS` = 5 неверных попыток код аннулируется (429);
  - повторная отправка не чаще раза в 30 с, не больше 10 в час на адрес (429);
  - код выбирается равномерно (rejection sampling);
  - в явном dev-режиме лимиты отправки отключены: код и так отдаётся запрашивающему.
- **Тестирование:** `directory::tests::email_codes_are_hashed_single_use_and_limited`.
- **Результат:** PASS.
- **Остаточный риск.**
  - Rate limit по IP и устройству не введён: лимит считается по адресу почты. Массовые запросы к множеству разных адресов (спам письмами) ограничены только SMTP-провайдером — P1.
  - Ticket после сброса пароля действует для одного входа — так задумано (`login_checked` его гасит).

## AQUA-SEC-006 — отравление magic-link через Host

- **Файл:** `lib.rs:1043-1051`.
- **Описание.**
  1. Атакующий запрашивает код для почты жертвы со своим `nonce` и `Host: evil.example`.
  2. Сервер отправляет жертве письмо со ссылкой на evil.example.
  3. Атакующий узнаёт токен ссылки, подтверждает его на настоящем сервере и через `poll_link` получает код.
- **Исправление.** `link_base` берёт адрес из `AQUA_PUBLIC_URL`, `public_url` федерации или найденного `public::url()`. `Host` принимается, только если совпадает с одним из них или является частным или loopback IP.
- **Тестирование:** NOT TESTED интеграционно (нужен сервер с SMTP). Код прочитан.
- **Остаточный риск:** сервер в LAN без `AQUA_PUBLIC_URL`, к которому обращаются по доменному имени, больше не отправляет ссылку «Это я». Код в письме работает.

## CZ-SEC-001 — CeZeOs: demo-вход через подменённый Host

### AQUA-SEC-007 — одноразовые prekeys расходовались без входа
- **Было:** `GET /v1/bundle/:user` без токена каждый раз снимал один OPK (`local_bundle` → `opks.pop_front()`). Любой мог опустошить запас OPK любого человека.
- **Стало:**
  - без токена — bundle без OPK и без поиска по сети;
  - с токеном — до 30 OPK сразу, затем один в 10 с (`OPK_BURST`/`OPK_RATE`, корзина `BotLimits`);
  - приложение отправляет токен при запросе bundle.
- **Тесты:** `full_authenticated_e2e_conversation` (анонимный запрос → без OPK), `two_relays_act_as_one` (анонимный запрос через сеть → 404, с токеном → bundle), проверка OPK после «перезапуска».
- **Остаточный риск:** зарегистрированный аккаунт может расходовать по одному OPK в 10 с на каждого человека. Ограничения по паре вызывающий→цель нет.

### AQUA-SEC-008 — OPK сгорал до проверки первого сообщения; replay после перезапуска
- **Было:**
  - `take_one_time_prekey` удалял OPK до `Session::accept_initial`: подделанное или битое первое сообщение сжигало ключ.
  - Набор уже расшифрованных первых сообщений жил только в памяти: после перезапуска то же первое сообщение снова открывало сессию.
- **Стало:**
  - `Vault::peek_one_time_prekey`, удаление — после успеха;
  - хеши первых сообщений, открывших сессию (последние 2048), хранятся в vault (`seen-initials`, запись зашифрована).
- **Тесты:** `vault::tests` (peek не удаляет). Код клиента локально не собирается (нет `ort`), его проверяет CI.

### AQUA-SEC-009 (часть) — повтор федеративных запросов
- **Было:** подпись `x-aqua-fed` действовала все ±5 минут сколько угодно раз.
- **Стало:**
  - приёмник принимает каждую подпись один раз (`first_use`);
  - отправитель делает метку времени строго возрастающей: одинаковые запросы в одну миллисекунду раньше давали одинаковую подпись, и первая версия защиты от повтора уронила тест `changes_are_pushed_to_peers`.
  - Совместимо в обе стороны.
- **Тесты:** `cursor_tests::a_signature_is_taken_once`, все 5 тестов федерации.
- **Не сделано:**
  - собственные ключи узлов вместо общего секрета;
  - получатель в подписи.
  - Это смена модели доверия: кто авторитетен для аккаунта, как узлы узнают ключи друг друга. Без неё ключи узлов не отнимают у держателя секрета возможность переписать любой аккаунт. Нужен проект — в FEDERATION_SECURITY (будет создан) — и согласование с владельцем.

## AQUA-SEC-012 — состояние на 1.21.0-24

- Подпись `SHA256SUMS.txt` (1.21.0-23) не проверялась в запасном пути клиента (`updates.rs::web_check`, когда не отвечают ни API GitHub, ни `updates.json`): кто мог подменить файл на странице выпуска, подменял и строку суммы. Исправлено в 1.21.0-24.
- Приложение сервера скачивает только файлы выпусков этого репозитория (`DOWNLOAD_PREFIX`), раньше — любой адрес `https://github.com/`.
- Подпись не называла версию: источник списка выпусков мог выдать старый подписанный выпуск за новый (откат). Теперь `release.yml` кладёт в суммы строку файла `VERSION`, и все три обновлятеля требуют её (`aqua_core::release::sums_trusted_for`). Проверится на деле только при обновлении с 1.21.0-24 на следующий выпуск.
- Мессенджер брал адрес и контрольную сумму файла у интерфейса (webview), а новизну проверял только интерфейс. Теперь `update_download` берёт только то, что нашла и проверила `update_check` (и только новее своей версии), а `update_install` — только этот скачанный файл, сверив его ещё раз.
- Консольный сервер запускал подготовленный бинарник из папки данных без проверки; теперь сверяет его с сохранённым подписанным списком. Адрес загрузки — только выпуски этого репозитория.
- Приложение сервера перед установкой сверяет скачанный файл ещё раз.
- **Перепроверка F (27.11).** Пре-выпуск или выпуск решалось по неподписанным данным ленты: флаг `prerelease` (API, `updates.json`) и ключ `stable` в `updates.json`. Кто отвечал вместо ленты (домен сайта, зеркало), мог выдать подписанный пре-выпуск всем, хотя пре-выпуски — только «Тестер» (владелец). Теперь решает номер версии, а его называет подписанная строка `VERSION`: `aqua_core::release::channel_allows`, во всех трёх обновлятелях. Тесты: `pre_releases_only_for_testers`, `selfupdate::a_pre_release_marked_stable_is_not_for_everyone` (падали до исправления — проверено), тот же тест в приложении сервера и `only_a_newer_offered_file` в мессенджере (только CI: локально не собираются).
- **Перепроверка F, запуск (27.11, второй проход).** Консольный сервер читает файл обновления один раз, сверяет хеш этих байтов с подписанным списком, и дальше работает только с ними: пишет их на место бинарника (`put_in_place`, раньше — `fs::copy` файла второй раз) и запускает их же (`launch`), во всех путях — `run_newest`, `restart_into` (кнопка панели, таймер), после `systemctl restart`. Запуска «по имени» после проверки больше нет; не удалось запустить проверенное — сервер остаётся на своей версии (раньше — запуск по имени).
  - Linux: запечатанный memfd (`F_SEAL_WRITE|GROW|SHRINK|SEAL` — изменить не может никто, и мы тоже) + `execveat(AT_EMPTY_PATH)`, без `/proc`. Тест `the_checked_bytes_run_sealed`: запись и усечение memfd отклоняются, двоичный файл из него запускается. `vm.memfd_noexec=2` или ядро < 3.19 — запуска нет (fail-closed).
  - Windows: файл открыт без `FILE_SHARE_WRITE/DELETE` с проверки до запуска — записать, переименовать, удалить его в это время нельзя. **Не проверено**: Windows в CI для сервера не запускается.
  - macOS и прочие Unix: копия проверенных байтов в своей папке 0700 во временной папке пользователя. Защищает от другого пользователя с правом записи в папку данных, не от того же пользователя. **Не проверено** на macOS.
  - Модель угроз: тот, кто пишет в папку *установки* бинарника (не данных) тем же пользователем, может подменить бинарник и без обновления — вне модели. После `systemctl restart` systemd запускает файл из `ExecStart` по имени: это либо проверенные байты, записанные поверх (папка установки — вне модели), либо старый бинарник, который сам проверяет и запускает подготовленный (`run_newest`).
  - Канал проверяется ещё раз перед установкой (выключили «Тестер» после скачивания — пре-выпуск не ставится) во всех трёх обновлятелях; при старте подготовленный пре-выпуск не запускается, если «Тестер» выключен и он здесь ещё не работал (работавший — запускается: откат на старый бинарник поверх тех же данных опаснее).
  - Строгий формат версии (`release::version_ok`: `X.Y.Z` или `X.Y.Z-N`, только цифры, без ведущих нулей) — внутри `channel_allows`, во всех путях. Тесты `versions_are_strict`, `a_pre_release_with_a_bad_number_is_never_picked`.
- **Перепроверка F, остальное (27.11).**
  - `tools/aquamarine-site.sh` ставит сайт, только если `SHA256SUMS.txt` выпуска подписан ключом выпусков (вшит в скрипт; `release-signing-check.yml` сверяет его с `UPDATE_PUBKEY`), называет этот выпуск (`VERSION`) и содержит хеш архива. Тест `tools/site-verify-test.sh` (в CI): подменённый архив, чужая версия, изменённый после подписи список, нет подписи, другой ключ — отказ. Проверено вживую: v1.21.0-24 ставится, v1.21.0 (до подписи выпусков) — отказ. Нужен `openssl` ≥ 1.1.1 (Termux: `pkg install openssl-tool`).
  - Ключ выпусков `d5753e7d…5d96` найден в бинарнике v1.21.0-24 и проверяет подпись этого выпуска — подпись выпусков работает на деле.
  - Приложение сервера на Android по-прежнему открывает APK в браузере. Принято: Android ставит обновление только с той же подписью приложения и не ниже `versionCode` — чужой или старый APK не встанет; внутри приложения файл не сверяется.
  - SSH (приложение сервера, решение владельца 27.11): первое подключение останавливается на ключе машины — пароль и ключ входа ещё не отправлены (раньше приложение принимало любой ключ и сразу входило). Окно показывает отпечаток SHA-256 и как сверить его на самой машине; сохраняется только подтверждённый (`remote_trust` принимает лишь тот отпечаток, что машина показала).
