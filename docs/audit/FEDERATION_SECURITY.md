# FEDERATION_SECURITY — модель доверия федерации Aquamarine

Состояние на 1.21.0-26 (ветка `claude/federation-identity`). Решение владельца от 26.11: обязательная криптографическая идентичность серверов, контролируемая миграция, без автоматического перехода в небезопасный режим.

Что проверено: только тестами в CI и локально (`cargo test -p aqua-server`). На живой сети из нескольких серверов разных версий — **не проверено**.

## Кто есть кто
- **Общий секрет сети** (`secret`): HMAC над запросом (`x-aqua-fed`). После перехода на ключи годится только чтобы представиться: `hello`, `ping`, `names/hello` — узел попадает в «Ожидают допуска».
- **Ключ узла** (Ed25519): свой у каждого сервера, `aqua-fed-node.key` (0600), в `aqua-federation.json` не пишется. id узла — первые 16 байт SHA-256 открытого ключа.
- **Закрепление** (`pins`): адрес → id → ключ; `role` = `network` | `names` (соло-сервер реестра имён), `since`, `rot_seq`.
- **Подпись v2** (`x-aqua-fed2`): Ed25519 над методом, путём с query, временем, nonce, id отправителя и получателя, SHA-256 тела. Ответ подписывается ключом отвечающего (`x-aqua-fed2-resp`) поверх заголовка запроса, статуса и тела.
- **Отправитель** (`fed.rs::verify_from`, `Sender`): `Node(id)` — проверенная подпись v2 закреплённого узла; `Secret` — только общий секрет.

## Режим ключей (`auth_mode`)
| Состояние | Когда | Что принимается |
|---|---|---|
| `transition` | Первый запуск 1.21.0-26; срок `auth_deadline` = +14 дней | v2 от закреплённых; секрет — от остальных |
| `enforced` | Ключи всех соседей известны, срок вышел или кнопка админа | Только v2; секрет — только hello/ping/names-hello |
| окно для старых (`legacy_until`) | Только админ, ≤ 7 дней, `confirm: true`, журнал | Как `transition`, пока не истечёт; `auth_mode` остаётся `enforced` |

- Переход `transition → enforced` — `FedConfig::settle` (`fed.rs:362`), вызывается в `Fed::new` и сразу сохраняется на диск. Обратно автоматически — никогда: `enforced()` (`fed.rs:736`) больше не считается по списку соседей на каждый запрос (раньше любой узел без ключа в списке — от админа, `AQUA_FED_PEERS`, hello или выдуманный `tunnel:` — выключал строгий режим).
- Неизвестное значение `auth_mode` в файле → `enforced`.
- `AQUA_FED_AUTH=enforced` только ужесточает: окно для старых открыть нельзя.
- Срок 14 дней выбран нами — владелец срок не называл (сообщено в отчёте). Предупреждение за 3 дня — в панелях.

## Закрепление ключей (`decide_pin`, `fed.rs:1796`; `pin_change`, `fed.rs:1964`)
| Что пришло в hello | Что происходит |
|---|---|
| Первый ключ для адреса | Свой ключ: токен приглашения или поручительство сервера сети; без них — только в переходный период и только адреса из своего списка. `http`-адрес обязан подтвердить ключ: подписанный ping на этот id, ответ подписан этим ключом (`proves_address`, `fed.rs:2033`). `tunnel:` подтвердить нельзя — только токен, поручительство или админ |
| Ключ сменился, цепочка подписей | `follow_rotations` (`fed.rs:1998`): каждый шаг `aqua-fed-rotate-v2\n{url}\n{old_id}\n{new_pub}\n{seq}` подписан предыдущим ключом, `seq` растёт, не больше 8 шагов; пройденные id попадают в `retired` и больше не принимаются. Поле `rotated` (1.21.0-23/24) — один шаг |
| Другой ключ без подписи | `Conflict`: в «Ожидают допуска» с `conflict: true`; решает админ. Свежий токен приглашения заменяет ключ (сервер потерял ключ) |
| Тот же ключ на новом адресе | `Moved`: после подтверждения адреса закрепление, список соседей и курсоры переезжают |

## Обратный канал (`fedtunnel.rs`)
- Найдено чтением кода и подтверждено тестом `tunnel_peer_with_pinned_key_syncs_both_ways`: запросы через канал шли без `x-aqua-version`, и каждый получал `426`; ответы не подписывались ключом, и узел с закреплённым ключом их отбрасывал. Теперь запрос несёт версию, которую опрошенный сервер сам назвал в `/v1/stats` (и только допустимую), а роутер канала подписывает ответы (`run_local`, `fedtunnel.rs:309`).
- `h_poll` / `h_reply` (`fedtunnel.rs:145`, `:194`): только тот, чей ключ закреплён за этим id (`speaks_for`, `fed.rs:940`); секретом — пока id ни за кем не закреплён и ключи не обязательны. Ответ принимается только на запросы своего канала. Адрес убирается из списка только по слову его владельца.

## Повтор (`replay.rs`)
- Подпись принимается один раз. v2-запрос расходует и свою `x-aqua-fed` (раньше её можно было повторить, сняв `x-aqua-fed2`).
- Квота 50 000 на отправителя (id узла; все держатели секрета — один отправитель), всего 400 000. Очистка по индексу времени — каждая запись просматривается один раз.
- Файл синхронизируется раз в секунду и при чистой остановке (Ctrl+C, стоп в панели, самообновление, перезапуск), которая оставляет метку `.clean`. Старт без метки (сбой, отключение питания, старая версия) не принимает подписи, сделанные до старта.
- Блокировка `.lock`: второй процесс (новый при обновлении на Windows) отказывает, пока первый не завершится, затем читает записанное им.
- Пропуски `aqpass`: использованные nonce — в той же таблице, на диске.

## Синхронизация
- Курсоры (`fed_cursors`, `directory.rs:2957`): users, backups, hist, names, tombs. Курсор не двигается за строку, которую не удалось записать (`FedApplied.failed`), прочитать или разобрать. Медиа профиля скачивается до записи аккаунта; три неудачи подряд — без него.
- `users.updated_at` локальных изменений строго растёт (триггеры, `directory.rs:931`). Раньше аккаунт, созданный в ту же секунду, мог получить время меньше курсора соседа и не синхронизироваться никогда (нашёл тест `cursor_survives_restart`).
- `POST /v1/admin/fed/resync {peer?, stream?}` — прочитать заново (после восстановления базы).

## Удаление аккаунтов (надгробия)
- Админ удаляет аккаунт (`delete_account`, `lib.rs:3319`): до удаления создаётся надгробие, подписанное ключом узла: `aqua-fed-tomb-v1\n{uid}\n{username}\n{created_at}\n{deleted_at}\n{origin}`.
- `GET /v1/fed/tombs`: свои и переданные дальше. Принимаются только с подписью закреплённого неотозванного узла-источника (`verify_tomb`, `fed.rs:709`); повторное применение ничего не меняет; соединения удалённого закрываются; не больше 20 в час от одного источника автоматически — остальные ждут.
- Поколение (`created_at` ≤ надгробия) больше не принимается: `fed_apply_user`, `fed_apply_name`, пропуск для удалённого ID. Повторная регистрация (новое `created_at`, в том числе тот же @ник) — разрешена.

## Что принимается от соседей
- Аккаунты — только от узлов роли `network`; строки ботов и строки «из будущего» (`updated_at` > сейчас + 5 мин) отклоняются; e-mail другого аккаунта (другой ID) не перехватывается.
- Реестр имён: более «старая» заявка переименовывает наш аккаунт, только если обе созданы в пределах 10 минут друг от друга и наш моложе 10 минут (одновременная регистрация). Отвергнутая заявка не записывается и не передаётся дальше. **Остаётся:** заявки в реестре не подписаны — узел реестра может выдумать «более старую» заявку на имя, которого у нас нет (только запись в чужом реестре), или отнять имя у аккаунта в первые 10 минут его жизни.
- Надгробия, подписанные ключом узла до его смены, принимаются по сохранённому старому ключу (`retired_keys`), но только с `deleted_at` не позже момента, когда мы перешли на новый ключ.
- `h_deliver` / `h_webapp_init`: отправитель (пользователь) должен быть известным, не забаненным человеком; лимит 6000 / 120 в минуту на узел. **Это смягчение, а не доказательство авторства**: узел сети по-прежнему может назвать любого известного отправителя. Подлинность сообщения обеспечивает сквозное шифрование на устройствах. Конверты, которые сервер забирает из чужих очередей (`inboxes2`), эту проверку не проходят.
- Пропуск `aqpass` v2: подпись ключом домашнего узла (`pass_signed_by`, `fed.rs:676`); при обязательных ключах пропуск, сделанный одним секретом, не принимается.

## Отложено (ограничения)
| Что | Почему |
|---|---|
| Подписи пользователя на конвертах | Нужна смена протокола клиента |
| E-mail в запечатанном виде | Нужен формат и миграция клиентов |
| Удаление аккаунта с подписью устройства | Сейчас удаляет только админ сервера |
| Распространение отзывов ключей | Отзыв действует на том сервере, где его сделали |
| Резервная копия ключа узла | Потеря папки данных = новый ключ = конфликт у соседей |
| Отзыв токена приглашения в панели | Не сделан |

## Риски перехода
- Срок отрежет выключенные и необновлённые серверы: после него они только в «Ожидают допуска».
- Исправление обратного канала вызовет большую синхронизацию: каналы, которые раньше молча не работали, начнут передавать всё накопленное.
- Docker без тома `/data`: новый ключ при каждом перезапуске → конфликт ключа у соседей при каждом старте.
- Сервер с базой, восстановленной из копии, должен сделать resync.
- Лимит 20 удалений в час задержит массовое законное удаление.
- Первый старт 1.21.0-26 после старой версии — «нечистый» для таблицы повторов: подписи последних 5 минут до обновления отклоняются, соседи подпишут заново.
