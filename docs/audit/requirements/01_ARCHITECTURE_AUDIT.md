# ARCHITECTURE AUDIT — CeZeOs + Aquamarine

## 1. Цель

Провести полное исследование архитектуры CeZeOs и Aquamarine. Установить реальное состояние проектов, определить взаимосвязи компонентов, выявить архитектурные дефекты и подготовить безопасный план улучшения.

Основные репозитории:

* https://github.com/applememestm-pixel/cezeos
* https://github.com/applememestm-pixel/Aquamarine

## 2. Инвентаризация

Исследовать:

* Все каталоги и исходные файлы.
* Backend.
* Frontend.
* API.
* Базы данных.
* IPC.
* Сетевые протоколы.
* Криптографические модули.
* Федерацию.
* Хранилища.
* Медиаобработку.
* Сборочные системы.
* Конфигурацию.
* CI/CD.
* Тесты.
* Зависимости.

Не ограничиваться README и главными файлами.

Для каждого модуля составить карточку:

1. Назначение.
2. Технологии.
3. Точка входа.
4. Зависимости.
5. Входные данные.
6. Выходные данные.
7. Связанные модули.
8. Состояние реализации.
9. Известные ограничения.
10. Обнаруженные проблемы.

## 3. Карта архитектуры

Создать:

* Общую архитектурную диаграмму.
* Диаграмму потоков данных.
* Диаграмму авторизации.
* Диаграмму отправки сообщений.
* Диаграмму доставки сообщений.
* Диаграмму федерации.
* Диаграмму хранения медиа.
* Диаграмму синхронизации устройств.
* Диаграмму взаимодействия CeZeOs ID и Aquamarine.

Отдельно описать границы ответственности двух проектов.

CeZeOs — самостоятельная социальная платформа.

Aquamarine — самостоятельный коммуникационный слой.

Общие механизмы не должны создавать ненужную связанность проектов.

## 6. Архитектурные риски

Искать:

* Циклические зависимости.
* Дублирование логики.
* Нарушение границ модулей.
* Сильную связанность.
* Неправильное управление состоянием.
* Необоснованные глобальные состояния.
* Неуправляемые фоновые задачи.
* Слабые границы доверия.
* Несогласованные форматы данных.
* Небезопасные миграции.
* Дублирование источников истины.

## 7. Целевая архитектура

Подготовить предложения по:

* CeZeOs ID.
* Переносимости аккаунтов.
* Независимым регионам.
* Федерации.
* Общей медиаплатформе.
* Developer Platform.
* Единому поиску.
* Интеграциям.
* Управлению устройствами.
* Offline-first.

Не превращать продукты в монолит.

## 8. Формат результатов

Создать:

* ARCHITECTURE_MAP.md
* MODULE_INVENTORY.md
* DATA_FLOW.md
* DEPENDENCY_MAP.md
* ARCHITECTURE_ISSUES.md
* TARGET_ARCHITECTURE.md

Для каждой проблемы указать конкретные файлы, строки, доказательства, критичность и способ исправления.

Не выдавать предположение за подтверждённый дефект.

## 9. Реализация

Исправлять архитектурные проблемы постепенно.

Не переписывать весь проект ради эстетики.

Не ломать API и существующие пользовательские данные.

Каждое существенное изменение сопровождать тестами и описанием миграции.

## 10. Критерий готовности

Должна существовать полная карта архитектуры обоих проектов, понятные границы компонентов, подтверждённый список дефектов и реалистичный план улучшений.
