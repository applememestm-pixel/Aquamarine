# Сеть серверов Aquamarine — черновик плана

Статус: черновик для обсуждения (пункты 12–14). Кода ещё нет. Старый Java-сервер
(`D:\pipo-server`, пакет `cluster`) прочитаем после `tools\copy-pipo-server.bat`.

## Что уже помогает
Сообщения шифруются от устройства до устройства (X3DH + Double Ratchet).
Сервер видит только конверты, публичные профили и зашифрованные файлы. Поэтому
сервер — это «почтальон», и почтальонов может быть много, им не нужно доверять.

## 1. Режимы сервера
| Режим | Кто может подключаться | Синхронизация |
|---|---|---|
| **Solo** | только разрешённые IP / аккаунты (список в панели админа) | нет, автономный |
| **Shared** | все | постоянно обменивается данными с другими shared-серверами |

Список разрешённых IP / аккаунтов — таблица `acl` на сервере плюс вкладка в
панели сервера (`server-gui.ps1` → позже нормальная веб-панель).

## 2. Общая сеть: «сервер 0» и преемники
* У каждого узла есть ключ Ed25519 (`node_id`). Узлы знают друг друга через gossip:
  каждый периодически рассылает соседям `{node_id, адреса, аптайм, нагрузку,
  версию состояния}` с подписью.
* **Сервер 0** — координатор: выдаёт версии каталога пользователей и
  порядок применения изменений.
* Если сервер 0 молчит дольше таймаута, остальные выбирают нового координатора
  по **репутации**: аптайм за 30 дней × успешные доставки × (1 − потери) и
  тайбрейк по `node_id`. Это как выборы лидера в Raft, только с весом.
  Вернувшийся сервер 0 сначала догоняет состояние и лишь потом снова может стать
  координатором.
* **Что синхронизируется:**
  * Каталог пользователей (username → ключ, профиль, ACL фото). Это журнал
    изменений с версиями: CRDT по принципу «последняя запись по версии побеждает»
    и с проверкой подписи владельца.
  * Зашифрованные файлы (blob по CID). Реплицируются лениво, по запросу и в
    популярные узлы.
  * Очереди офлайн-конвертов. Конверт хранится на «домашних» узлах получателя:
    2–3 узла по rendezvous-хэшу от username.

## 3. Подключение клиента
Клиент хранит список известных узлов и подписанный «bootstrap»-список. Он меряет
RTT и подключается к ближайшим живым узлам (2 соединения: основное и запасное).
Сообщение уходит на свой узел, тот пересылает на домашние узлы получателя.

## 4. Свой mesh (обсудим отдельно)
Узлы соединены постоянными туннелями (QUIC или WebSocket поверх TLS) с
маршрутизацией по «соседям»:
* сначала полная сетка до 20–30 узлов;
* потом структурированный DHT (Kademlia) для поиска домашних узлов.

## 5. Запуск сервера на любой технике
Один бинарник `aqua-server` (Rust) собирается под Windows / Linux / macOS / ARM
(Raspberry, Android через Termux). Плюс образ Docker и режим «встроенный сервер»
внутри клиента: телефон или ПК становится небольшим узлом с ограничением трафика.

## 6. Белые списки (обход блокировок)
Два варианта, можно оба:
1. **Пограничные узлы в «белой» сети** (Yandex Cloud / VK Cloud).
   * Это тонкий ретранслятор: принимает TLS на 443 и пересылает трафик на наши
     узлы (ПК, серверы).
   * Контента он не видит: всё уже зашифровано от устройства до устройства.
   * Дёшево; это единственная арендуемая часть.
2. **Маскировка трафика** (идея из GitHub-проекта).
   * Транспорт-плагин заворачивает наши кадры в трафик, похожий на разрешённый
     сервис.
   * Нужно сначала разобрать конкретный проект: что именно он подменяет, его
     надёжность и юридические риски для аренды у этих же облаков.
   * Делать его как подключаемый транспорт (`pluggable transport`), чтобы ядро не
     зависело от способа маскировки.

## Порядок работ (предложение)
1. ACL и режим Solo в текущем сервере, вкладка в панели.
2. Идентичность узла, gossip, список узлов в клиенте (выбор ближайшего).
3. Репликация каталога и blob'ов, домашние узлы для офлайн-очередей.
4. Выборы координатора вместо сервера 0.
5. Пограничный ретранслятор для облака.
6. Pluggable transports (маскировка), затем свой mesh / DHT.

## Реализовано (сессия 42)

### Подключение через сервер (прокси)
Настройки → Аккаунт и сервер → «Подключение через сервер». Поле SOCKS5-адреса
(`socks5://127.0.0.1:1080`). Когда оно задано, весь трафик клиента (HTTP и
релейный WebSocket) идёт через этот прокси; пусто — прямое подключение.
Хранится в `proxy.txt` рядом с хранилищем, применяется при следующем
подключении. Клиент сам туннель не запускает — он только ходит через прокси.

**Как связать с OpenFlux (делаешь ты, отдельно от Aquamarine):**
```bash
# на выходном узле (любая ОС, без root):
./openflux --role=exit --mode=l4 --transport=<...> --url="<...>"
# на своём ПК: поднять локальный SOCKS5, который ходит через туннель:
./openflux --role=client --inbound=socks5 --transport=<...> --url="<...>"
# → в Aquamarine вписать socks5://127.0.0.1:1080
```
Детали туннеля и выбор транспорта — на стороне OpenFlux (его README/доки).
Aquamarine в это не вмешивается: для него это обычный прокси.

### Панель администратора сервера
`http://<адрес-сервера>/admin` — страница в неоновом стиле клиента.
Включается переменной окружения `AQUA_ADMIN_TOKEN` (без неё — 404).
- Живая статистика: аккаунты, онлайн, боты, блобы, объём, аптайм.
- Контроль доступа: переключатель **invite-only (solo mode)** + белый список
  почт, которым разрешена регистрация. Это обычный контроль доступа к своему
  релею; E2EE не затрагивается — сервер по-прежнему пересылает только
  зашифрованные конверты.
- Запросы: `GET /v1/admin/stats`, `POST /v1/admin/config` (Bearer-токен).
  Политика хранится в `aqua-admin.json`.

Это первый кирпич режима Solo из плана выше. Следующее (по-прежнему черновик):
репликация между Shared-серверами, выборы координатора, mesh.

### Сборка на все платформы
- `.github/workflows/release.yml` — матрица Windows / macOS (arm64+x64) /
  Linux собирает клиент (Tauri: nsis/msi, dmg, AppImage/deb/rpm) и сервер
  (вкл. linux-arm64). На теге `v*` всё прикладывается к GitHub Release.
- `build-all.sh` — локальная сборка под macOS/Linux (аналог `build-all.bat`).
- `tauri.conf.json`: `targets` = nsis/app/dmg/appimage/deb/rpm — каждая ОС
  делает свои инсталляторы.
