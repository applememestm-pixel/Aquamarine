# Федерация ретрансляторов

> Часть [технической документации](README.md). Реализация — `crates/aqua-server/src/fed.rs`; методы — [api.md](api.md#16-федерация).

## 1. Принцип

Ретранслятор — «почтальон»: он видит конверты, публичные профили и зашифрованные файлы, но не содержимое. Поэтому ретрансляторов может быть несколько и им не нужно доверять друг другу больше, чем одному. Несколько ретрансляторов образуют единую сеть: пользователь любого узла пишет пользователю любого другого, а при отказе узла клиент переходит на соседний.

## 2. Настройка

При первом входе в панель администратора узел спрашивает режим: **один** (своя база, ни с кем не синхронизируется) или **в сети**. Режим меняется во вкладке «Федерация».

Проще всего собрать сеть кодом приглашения: на одном узле «Федерация → Пригласить» показывает код `aquafed:…` (адрес узла и секрет сети в base64url), на другом его вставляют в «Войти в сеть». Дальше узлы знакомятся сами: раз в 3 минуты каждый отправляет соседям `POST /v1/fed/hello` со своим адресом и списком соседей, и получатель добавляет тех из них, кто отвечает на подписанный `GET /v1/fed/ping` тем же секретом. Вкладка «Федерация» также показывает другие ретрансляторы — найденные в локальной сети (опрос `/24` на том же порту) и в публичном списке серверов — с пингом и пометкой, в той же ли они сети.

Вручную узлы настраиваются так:

- общий секрет — `AQUA_FED_SECRET` или панель администратора (не короче 16 символов);
- перечень адресов соседей — `AQUA_FED_PEERS` (через запятую);
- свой публичный адрес — `AQUA_PUBLIC_URL` (его узнают клиенты и соседи).

Настройки из панели хранятся в `aqua-federation.json` и применяются без перезапуска.

## 3. Подпись запросов

Каждый межсерверный запрос подписывается заголовком:

```
x-aqua-fed: <unix_ms>.<hex HMAC-SHA256(secret, METHOD "\n" PATH "\n" unix_ms "\n" hex(SHA-256(body)))>
```

Допустимое расхождение часов — ±5 минут. Подпись покрывает метод, путь с параметрами и тело.

С 1.2.0 ретранслятор называет в запросах свою версию (`User-Agent: aqua-server/<версия>`) и не обслуживает соседей старше 1.2.0 (`426`). Сам он тоже не обращается к соседу, у которого в `/v1/stats` нет `version` ≥ 1.2.0 (проверка раз в 10 минут). Причина: старые ретрансляторы не знают двухэтапной проверки, и в скопированную к ним учётную запись можно было бы войти без кода.

### 3.1. Ключи узлов (обязательны с 1.21.0-26)

У каждого сервера свой ключ Ed25519 (`aqua-fed-node.key`, 0600). Серверы закрепляют ключи друг друга и подписывают запросы `x-aqua-fed2`; ответы на них подписываются ключом отвечающего (`x-aqua-fed2-resp`). Модель доверия, угрозы и что осталось — в [audit/FEDERATION_SECURITY.md](audit/FEDERATION_SECURITY.md).

- **Переходный период.** При первом запуске 1.21.0-26 сеть получает срок — **14 дней** (`auth_deadline` в `aqua-federation.json`). Пока он идёт, серверы без ключа (старые версии) ещё работают по одному общему секрету.
- **Только по ключам** включается само и навсегда: когда ключи всех соседей известны, когда срок вышел, или кнопкой «Только по ключам — сейчас». Обратно само не возвращается: ни сосед без ключа в списке, ни перезапуск, ни `AQUA_FED_PEERS` этого не отменят. После этого общий секрет годится только чтобы представиться (hello, ping, names-hello) — сервер попадает в «Ожидают допуска».
- **Окно для старых серверов** — кнопка «Пустить старые серверы на 1 день» (`POST /v1/admin/fed/auth {"action":"legacy","legacy_days":1..7,"confirm":true}`), с записью в журнал. Окно закрывается само. `AQUA_FED_AUTH=enforced` запрещает окно.
- **Отложить** срок можно, пока он идёт: «Отложить на 7 дней» (не дальше 14 дней от сегодня). За 3 дня панель предупреждает и показывает серверы без ключа.
- **Новый сервер** вступает по приглашению с токеном (или по поручительству сервера сети). Ключ закрепляется, только если адрес его подтверждает: подписанный `ping` на этот адрес, ответ подписан тем же ключом. Сервер за роутером (`tunnel:`) подтвердить адрес не может — только токен, поручительство или админ.
- **Смена ключа** («Новый ключ узла»): старый ключ подписывает новый; сосед, пропустивший несколько смен, идёт по цепочке (до 8 шагов). Другой ключ без подписи старого — **конфликт**: ждёт админа («Допустить сервер») или свежего токена приглашения (сервер потерял ключ).
- **Соло-серверы** закрепляются через names-hello с полями ключа и читают только реестр имён.
- **Где сейчас синхронизация** с каждым соседом хранится в базе (`fed_cursors`): перезапуск не тянет всё заново. Прочитать всё с начала — `POST /v1/admin/fed/resync {peer?, stream?}` (например, после восстановления базы из копии).
- **Удаление аккаунта** админом создаёт подписанное надгробие (`GET /v1/fed/tombs`): остальные серверы удаляют копию и больше её не принимают от серверов, не узнавших об удалении. Регистрация того же @имени заново разрешена. Не больше 20 удалений в час от одного сервера применяются сами, остальные ждут.

## 4. Функции

| Функция | Механизм |
|---|---|
| Уведомление об изменении | Узел раз в 1,5 с сравнивает отметку изменений (наибольшие `updated_at` таблиц `users` и `backups`). Если она сдвинулась, узел отправляет соседям `POST /v1/fed/poke`, и они сразу выполняют выборку. Без уведомлений выборка выполняется каждые 30 с |
| Репликация учётных записей | Узлы забирают у соседей строки `users` с `updated_at` больше курсора (страницами по 500); при конфликте побеждает более поздняя запись. Учётные записи ботов не реплицируются |
| Репликация медиа профилей | Если у принятой строки изменилась версия аватара, баннера или трека, узел сразу копирует файл у соседа и хранит у себя |
| Репликация резервных копий | Тем же способом, по `updated_at` |
| Доставка | Конверт пересылается узлу, к которому подключён получатель (`POST /v1/fed/deliver`). Если получатель не в сети ни на одном узле, конверт ждёт на исходном узле; узел, к которому получатель подключится, забирает его (`/v1/fed/inbox/:user`) |
| Ключи, вложения | При локальном отсутствии запрашиваются у соседей; целостность вложений проверяется по CID. Одноразовые ключи (OPK) не реплицируются, чтобы один ключ не был выдан дважды |
| Отказоустойчивость клиента | `GET /v1/fed/peers` возвращает публичные адреса узлов. Клиент хранит до 12 адресов и при недоступности текущего узла переподключается к следующему |

| Почта | Узел без своего SMTP просит соседа с почтой отправить письмо с кодом (`POST /v1/fed/mail`, подписано, не больше 5 писем на адрес за 10 минут). Пароль от почты никогда не покидает свой узел — соседу передаются только адрес, код и ссылка |
| Имена | Учётные записи сверяются по ID (`uid`, 10 цифр, не меняется), а не по @имени. Тот же ID под другим именем — смена имени: старая строка удаляется, старое имя пересылает на новое. То же @имя под другим ID — два разных человека (ретрансляторы работали отдельно, потом объединились): обе учётные записи остаются. Имя сохраняет более старая (при равенстве — меньший ID), вторая получает `имя_NNNN` (последние цифры ID, при занятости — больше цифр) — одинаково на всех узлах, без переговоров. Её владелец видит предупреждение и выбирает новое имя; его контакты переходят на новое имя сами, сверив ID (`GET /v1/users/by-id/:uid`) |

Узел в режиме «один» ничего не реплицирует. Когда он входит в сеть, его учётные записи расходятся по сети (при конфликте — более поздняя запись), а до этого изменения на нём не видны другим узлам.

Клиент может закрепить свой сервер («Сеть и прокси → Не уходить с этого сервера»): тогда он не переключается ни на более быстрый узел, ни на другой узел при отказе — только на другой адрес того же узла.

Не реплицируются: учётные записи ботов и их очереди, наборы стикеров (каждый узел импортирует свои), запечатанные послания и время последнего подключения ([sealed-messages.md](sealed-messages.md#5-ограничения)).

## 5. Режимы доступа

| Режим | Кто может зарегистрироваться | Включение |
|---|---|---|
| Открытый | Любой | По умолчанию |
| «Только по приглашению» | Правила из списка «Разрешённые» и коды приглашений | Панель администратора (`POST /v1/admin/config`), хранится в `aqua-admin.json` |

Правила списка (с 1.2.0-4), по одному в строке:

| Правило | Кого пускает |
|---|---|
| `@имя` (или `имя`) | Регистрацию с этим @именем |
| `*@сервер` | Любого, у кого есть пропуск с этого сервера сети |
| `@имя@сервер` | Человека `@имя` с этого сервера, с пропуском |
| адрес почты | Старые учётные записи (до 1.2.0-1) |

`сервер` — адрес без схемы: `relay.example.com` или `1.2.3.4:7777`.

**Пропуск** (`POST /v1/me/pass` → `{"pass", "expires", "home"}`) выдаёт сервер сети своему пользователю: `aqpass:` + base64url(JSON `{u, i, h, x, n, k, s}`) + `.` + hex HMAC-SHA256(секрет сети, `"aqpass|" ‖ payload`). С 1.21.0-26 `k` — id узла выдавшего сервера, `s` — подпись его ключом над `aqpass-v2\n{u}\n{i}\n{h}\n{x}\n{n}`; соло-сервер, у которого ключи обязательны, без верной подписи пропуск не примет. Старые серверы читают только HMAC. Работает 10 минут и один раз (использованные хранятся на диске). Его проверяет соло-сервер, у которого тот же секрет (см. раздел 5.1); пропуск передаётся в поле `invite` у `/v1/users/signup`. В приложении: «Настройки → Аккаунт и сервер → Пропуск на приватный сервер».

Режим ограничивает регистрацию на своём узле и не затрагивает E2EE.

### 5.1. Соло-сервер в реестре имён

Соло-сервер можно подключить к сети «ради имён»: в панели «Федерация» в режиме «Один» — «Вступить ради имён» с приглашением `aquafed:…` (`POST /v1/admin/fed/join {"invite", "names_only": true}`). Сервер остаётся соло (`mode = "solo"`, `FedConfig::registry()`):

- Он обменивается с сетью **только реестром имён**: `(uid, @имя, home, created_at)`. Учётные записи, профили, ключи, копии, история, письма и файлы не передаются ни в одну сторону.
- `GET /v1/fed/names?since=T` (подпись секретом сети) отдаёт свои учётные записи и уже известные чужие имена: `{"home", "mode", "names": [...]}`. Соло-сервер раз в 3 минуты говорит `POST /v1/fed/names/hello {"url"}`; сервер сети запоминает его в `solo_peers` и забирает его имена каждые 30 с. В ответ соло-сервер узнаёт остальные серверы сети.
- Чужие имена лежат в таблице `fed_names` и в поиске не показываются. @имя, занятое там, нельзя зарегистрировать или взять при смене имени (`409`).
- Если одно @имя всё же оказалось у двух учётных записей (зарегистрированы одновременно), имя остаётся у старшей (при равенстве — у меньшего ID), младшая получает `имя_` + хвост ID — так же, как при слиянии сети (раздел 4).

## 6. Подключение через прокси

Клиент направляет весь трафик к ретранслятору (HTTP и WebSocket) через SOCKS5, если адрес задан в «Настройки → Аккаунт и сервер → Подключение через сервер»: `socks5://` или `socks5h://` (имена разрешает прокси). Клиент сам туннель не поднимает — подходит любой локальный SOCKS5, например конец туннеля до своего узла за пределами фильтрующей сети.

## 7. Проверка

Интеграционные тесты `crates/aqua-server/tests/federation.rs` запускают два узла в одном процессе. Тест `changes_are_pushed_to_peers` проверяет, что учётная запись, аватар и резервная копия доходят до второго узла без ручной синхронизации, а ключи переживают перезапуск. Ключи узлов, обратный канал, курсоры, надгробия и пропуски проверяют тесты 1.21.0-26 — их список и что каждый доказывает, в [audit/FEDERATION_SECURITY.md](audit/FEDERATION_SECURITY.md#тесты).

## 8. Направления развития

Не реализовано; порядок может меняться:

1. Обмен списком узлов с подписью (gossip) вместо статического `AQUA_FED_PEERS` (ключи узлов есть с 1.21.0-23, обязательны с 1.21.0-26).
2. «Домашние» узлы получателя (2–3 по rendezvous-хешу имени) для офлайн-очередей.
3. Координатор каталога с выбором преемника по репутации (аптайм, успешные доставки).
4. Пограничный ретранслятор в разрешённой сети, который только пересылает TLS на узлы сети.
5. Подключаемые транспорты (маскировка трафика) и маршрутизация по соседям (Kademlia).
6. Ретранслятор на телефоне и встроенный узел в клиенте.


## Сервер за роутером: обратный канал (с 1.2.12-2)

Сервер дома без проброса порта может достучаться до публичного, а наоборот — нет. Поэтому каждый сервер держит к своим соседям долгий опрос `POST /v1/fed/tunnel` (подписан секретом сети, как всё в федерации). Когда сосед не отвечает напрямую — или у него вообще нет адреса, и он известен как `tunnel:<node>` — запросы к нему ставятся в очередь этого опроса; сосед выполняет их у себя и отвечает `POST /v1/fed/tunnel/reply`. Так синхронизация аккаунтов, резервных копий, истории, доставка конвертов и файлов идут в обе стороны.

Ничего настраивать не нужно: достаточно, чтобы сервер за роутером знал адрес публичного (вступил в сеть по его приглашению). В списке серверов такой сосед помечен «обратный канал».

С 1.21.0-26 опрос и ответы принимаются только от сервера, чей ключ закреплён за этим id (общим секретом — пока id ни за кем не закреплён и ключи не обязательны). Запросы, пришедшие по каналу, несут версию опрошенного сервера из его `/v1/stats` — до этого каждый такой запрос получал `426`, и обратный канал при закреплённых ключах не работал. Сервер за роутером не может подтвердить адрес, поэтому вступает только по приглашению с токеном.
