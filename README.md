# Aquamarine

**Система обмена сообщениями со сквозным шифрованием: настольный и мобильный клиент, самостоятельно размещаемый сервер-ретранслятор и федерация ретрансляторов.**

[Релизы](https://github.com/applememestm-pixel/Aquamarine/releases) · [Сайт](https://applememestm-pixel.github.io/aquamarine/) · [Изменения в 0.1.1](docs/releases/v0.1.1.md) · [Политика безопасности](SECURITY.md) · [Руководство по ботам](docs/BOTS.md) · [Журнал разработки](PROGRESS.md)

---

## Аннотация

Aquamarine — клиент-серверная система обмена сообщениями. Конфиденциальность переписки в ней обеспечивается сквозным шифрованием по протоколам X3DH и Double Ratchet.

- **Клиент** написан на Rust (ядро) и Svelte 5 (интерфейс) и упакован средой Tauri 2.
- **Сервер-ретранслятор** написан на Rust (axum, Tokio, SQLite) и не располагает ключами для расшифровки содержимого.

Документ описывает:

- архитектуру системы;
- криптографические механизмы и модель угроз;
- форматы хранения данных;
- механизм резервного копирования и переноса учётной записи;
- протокол федерации ретрансляторов;
- программный интерфейс ботов;
- известные ограничения;
- порядок сборки и развёртывания;
- лицензионный статус исходного кода и зависимостей.

## 1. Архитектура

### 1.1. Компоненты

| Компонент | Крейт или каталог | Назначение |
|---|---|---|
| Протокольное ядро | `crates/aqua-core` | Ключи, X3DH, Double Ratchet, форматы конвертов, шифрование файлов. Используется клиентом и сервером; сервер применяет его только для проверки подписей и форматов |
| Клиентское ядро | `crates/aqua-client-core` | Транспорт HTTP и WebSocket (в том числе через SOCKS5), зашифрованное хранилище (vault), управление предварительными ключами, резервные копии |
| Клиентское приложение | `crates/aqua-client-ui` | Команды Tauri (`src/`), интерфейс Svelte 5 (`ui/`), история, медиа, звонки, определение активности |
| Ретранслятор | `crates/aqua-server` | Сервис HTTP и WebSocket: каталог пользователей, раздача предварительных ключей, очередь конвертов, хранилище зашифрованных файлов, резервные копии, боты, федерация, панель администратора |

### 1.2. Схема взаимодействия

```
 ┌──────────── устройство A ────────────┐                         ┌──────────── устройство B ────────────┐
 │ Svelte 5 (WebView) ── IPC Tauri      │                         │      IPC Tauri ── Svelte 5 (WebView) │
 │ aqua-client-ui ── aqua-client-core   │                         │   aqua-client-core ── aqua-client-ui │
 │ vault.sqlite (ChaCha20-Poly1305)     │                         │     vault.sqlite (ChaCha20-Poly1305) │
 └──────────────────┬───────────────────┘                         └───────────────────┬──────────────────┘
                    │ HTTPS + WebSocket: зашифрованные конверты                       │
                    ▼                                                                 ▼
          ┌──────────────────┐    подписанные HMAC запросы федерации   ┌──────────────────┐
          │ aqua-server  R1  │ ◄─────────────────────────────────────► │ aqua-server  R2  │
          │ SQLite: каталог, │                                         │                  │
          │ очередь, копии   │                                         │                  │
          │ aqua-blobs/      │                                         │                  │
          └──────────────────┘                                         └──────────────────┘
 Медиапоток звонков идёт напрямую между устройствами (WebRTC, DTLS-SRTP); сигнализация — внутри сеансов E2EE.
```

### 1.3. Среда выполнения клиента

Интерфейс исполняется в системном WebView:

| ОС | WebView |
|---|---|
| Windows | WebView2 |
| macOS, iOS | WKWebView |
| Linux | WebKitGTK 4.1 |
| Android | Android System WebView |

Криптографические операции, ключевой материал, сетевой обмен и файловый ввод-вывод выполняются в процессе Rust. Интерфейс вызывает их через IPC Tauri. Права интерфейса ограничены декларацией `capabilities/default.json`.

## 2. Модель угроз

### 2.1. Противники

| Противник | Возможности | Последствия |
|---|---|---|
| Пассивный наблюдатель сети | Чтение трафика | Наблюдает трафик TLS к ретранслятору (если TLS используется) и трафик WebRTC (DTLS-SRTP). Содержимое недоступно |
| Оператор ретранслятора, честный, но любопытный | Чтение базы данных, журналов и памяти процесса | Получает метаданные (раздел 14). Содержимое сообщений, файлов, групп и резервных копий недоступно |
| Активный оператор ретранслятора | Подмена ответов сервера | Может подменить набор предварительных ключей при первом контакте (атака «человек посередине»). Подмену обнаруживает только сверка отпечатка ключа по независимому каналу (п. 4.4) |
| Похититель базы данных ретранслятора | Офлайн-анализ | Получает хеши PBKDF2 от производного секрета Argon2id, зашифрованные резервные копии и SHA-256 токенов ботов. Пароли, ключи копий и токены не раскрываются |
| Похититель устройства без доступа к системному хранилищу ключей | Чтение файлов | Записи хранилища зашифрованы. Настройки интерфейса и медиакэш не зашифрованы (раздел 10) |
| Похититель разблокированного устройства | Полный доступ к сеансу | Защиты нет, за исключением необязательного код-пароля приложения |

### 2.2. Допущения

1. Генератор случайных чисел ОС (`OsRng`) криптографически стоек.
2. Системное хранилище ключей (Secret Service, Keychain, Windows Credential Manager) не скомпрометировано.
3. Пользователь сверяет отпечатки ключей, если угроза активной подмены для него значима.
4. Реализации примитивов (dalek-cryptography, RustCrypto) корректны.

### 2.3. Вне рамок защиты

- сокрытие факта общения и графа связей от оператора ретранслятора;
- защита от вредоносного ПО на устройстве;
- переписка с ботами (раздел 12).

| Назначение | Алгоритм | Стандарт | Реализация |
|---|---|---|---|
| Согласование ключей | X25519 | RFC 7748 | `x25519-dalek` 2.0 |
| Подпись | Ed25519 | RFC 8032 | `ed25519-dalek` 2.2 |
| Аутентифицированное шифрование | ChaCha20-Poly1305, nonce 96 бит | RFC 8439 | `chacha20poly1305` 0.10 |
| Выработка ключей | HKDF-SHA256 | RFC 5869 | `hkdf` 0.12 |
| Цепочки ключей, токены, подпись запросов федерации | HMAC-SHA256 | RFC 2104 | `hmac` 0.12 |
| Идентификатор файла, хеш токена бота | SHA-256 | FIPS 180-4 | `sha2` 0.10 |
| Ключ резервной копии, производный секрет входа | Argon2id v1.3 | RFC 9106 | `argon2` 0.5 |
| Хранение секрета входа на сервере | PBKDF2-HMAC-SHA256, 120 000 итераций, соль 16 байт | RFC 8018 | собственная обёртка над `hmac` |
| Сжатие истории и копий | DEFLATE | RFC 1951 | `flate2` 1.1 |
| Ключ восстановления | 256 бит энтропии → 24 слова BIP-39, контрольная сумма 8 бит | BIP-0039 | собственная реализация |
| Сравнение секретов | Постоянное время | — | `subtle` 2.6 |
| Очистка памяти | Обнуление при освобождении | — | `zeroize` 1.9 |

## 4. Протокол сквозного шифрования

### 4.1. Ключи

Идентичность устройства состоит из двух независимых пар ключей:

- **IK_sig** (Ed25519) — подпись предварительных ключей и ответов на запрос аутентификации;
- **IK_dh** (X25519) — участие в X3DH.

В Signal одна пара выводится из другой (XEdDSA). Раздельные пары упрощают реализацию ценой 32 дополнительных байт в наборе ключей.

| Ключ | Описание | Политика |
|---|---|---|
| IK | Идентичность (Ed25519 + X25519) | Постоянный; переносится резервной копией |
| SPK | Подписанный предварительный ключ X25519 | Ротация каждые 7 суток |
| OPK | Одноразовые предварительные ключи X25519 | При остатке менее 10 пополняются до 50 |

### 4.2. X3DH

```
DH1 = DH(IK_A, SPK_B)   DH2 = DH(EK_A, IK_B)   DH3 = DH(EK_A, SPK_B)   DH4 = DH(EK_A, OPK_B)  (при наличии OPK)
SK  = HKDF-SHA256(salt = 0^32, ikm = 0xFF^32 ‖ DH1 ‖ DH2 ‖ DH3 [‖ DH4], info = "Aquamarine/X3DH v1", L = 32)
AD  = IK_A(X25519) ‖ IK_B(X25519)
```

Подпись SPK проверяется до использования ключа. Получатель уничтожает использованный OPK. Значение AD входит в AAD каждого шифротекста сеанса.

### 4.3. Double Ratchet

| Элемент | Реализация |
|---|---|
| Корневая цепочка | HKDF-SHA256, метка `Aquamarine/RootKDF v1` |
| Цепочки сообщений | HMAC-SHA256; байт `0x01` — ключ сообщения, байт `0x02` — следующий ключ цепочки |
| Ключ сообщения | HKDF, метка `Aquamarine/MsgKey v1` |
| Шифрование | ChaCha20-Poly1305 |

Свойства:

- **Прямая секретность.** Ключ сообщения используется однократно и уничтожается.
- **Восстановление после компрометации.** Каждый новый ключ DH собеседника подмешивает в корневой ключ свежий результат Диффи–Хеллмана.
- **Внеочередные сообщения.** Хранится до 1000 ключей пропущенных сообщений (`MAX_SKIP`). При превышении предела расшифровка прекращается с явной ошибкой.

### 4.4. Проверка собеседника

Окно «Отпечаток» показывает:

- полный открытый ключ X25519 собеседника в шестнадцатеричной записи;
- последовательность из 8 слов.

Защиту от подмены ключа ретранслятором даёт только сверка полной шестнадцатеричной записи по независимому каналу. Слова служат визуальной подсказкой и криптостойкостью не обладают: каждое кодирует один байт по модулю 24.

## 5. Транспорт и доставка

### 5.1. Доставка сообщения

1. Клиент запрашивает набор ключей получателя (`GET /v1/bundle/:user`) и проверяет подпись SPK.
2. После X3DH сообщение шифруется в рамках сеанса Double Ratchet.
3. Конверт `{from, to, kind, payload}` отправляется по WebSocket (`/v1/ws`):
   - поле `from` ретранслятор устанавливает сам по аутентифицированному сеансу;
   - поле `payload` для ретранслятора непрозрачно.
4. Ретранслятор выбирает первый применимый вариант:
   - доставить конверт на все активные подключения получателя;
   - переслать конверт узлу федерации, к которому подключён получатель (раздел 11);
   - поместить конверт в таблицу `inbox` (SQLite). Срок хранения — 30 суток; перезапуск сервера очередь не стирает.
5. При подключении получатель забирает конверты из локальной очереди и из очередей узлов федерации.

Через те же сеансы E2EE передаются служебные сообщения: отметки о прочтении, индикатор набора, присутствие, реакции, правки, удаления, голоса в опросах, снимки состояния групп, сигнализация звонков.

### 5.2. Звонки

- Сигнализация WebRTC (SDP, ICE) передаётся внутри сеансов E2EE.
- Медиапоток идёт напрямую между устройствами и защищён DTLS-SRTP (RFC 8827).
- Для обхода NAT используются публичные STUN-серверы `stun.l.google.com` и `stun.cloudflare.com`. Сервер TURN указывается пользователем; по умолчанию он не задан.
- Групповые звонки строятся по полносвязной схеме (mesh).

### 5.3. Сеанс и прокси

- Сеансовый токен ретранслятора действует 1 час. Клиент обновляет его заблаговременно, через 45 минут.
- Весь трафик к ретранслятору может направляться через SOCKS5: `socks5://`, либо `socks5h://` с разрешением имён на стороне прокси.

## 6. Файлы и медиаданные

### 6.1. Схема шифрования

1. Для каждого файла генерируются ключ (256 бит) и nonce (96 бит). Файл шифруется ChaCha20-Poly1305.
2. Идентификатор содержимого (CID) равен SHA-256 шифротекста. Ретранслятор отклоняет загрузку `POST /v1/blob/:cid`, если хеш тела не совпадает с CID.
3. Ключ, nonce, имя, размер и тип MIME передаются получателю сообщением E2EE.
4. Получатель загружает шифротекст, сверяет хеш и расшифровывает файл.

### 6.2. Хранение на ретрансляторе

Шифротексты хранятся на диске (`aqua-blobs/`, переменная `AQUA_BLOB_DIR`) как кэш доставки:

| Класс | Срок хранения | Предел размера |
|---|---|---|
| Обычные вложения | `AQUA_BLOB_TTL_HOURS`, по умолчанию 72 ч от последней загрузки; удаление — ежечасно | 210 МиБ на сервере, 200 МиБ в клиенте |
| Фото и баннеры групп (`?keep=1`) | 90 суток с момента последнего скачивания (скользящий срок) | 4 МиБ |

Получатель сохраняет расшифрованный файл в локальном кэше, поэтому истечение срока на сервере не делает полученное вложение недоступным.

### 6.3. Предварительная обработка

- Видео в режиме «со сжатием» перекодируется на устройстве в H.264 720p (`ffmpeg`).
- Изображения уменьшаются до 2560 px по большей стороне.
- Режим «файлом» передаёт оригинал без изменений.

## 7. Группы, супергруппы, каналы

Ретранслятор не хранит сведений о группах в открытом виде. У участников хранятся:

- состав, роли и права;
- комнаты супергруппы (текстовые, объявлений, голосовые) с названием, значком, описанием и переопределениями прав;
- правила, приветствие, акцентный цвет;
- фото и баннер (ссылки на зашифрованные вложения вместе с ключами). Баннер может быть изображением, GIF или коротким роликом: клиент перекодирует его в беззвучный цикл WebM (VP9, 3:1, до 960 пикселей, до 8 с, до 4 МиБ).

Состояние групп входит в зашифрованную резервную копию каждого участника и тем самым хранится на ретрансляторе и узлах федерации в зашифрованном виде (разделы 9 и 11).

Изменения распространяются снимками состояния с монотонно растущим номером версии (`version`). Получатель принимает снимок только от администратора текущей версии. Исключение — добавление участников, если настройки группы его разрешают.

Сообщение в группу шифруется отдельно для каждого участника его парным сеансом (fan-out). Стоимость отправки растёт как O(N).

| Тип | Участники | Возможности |
|---|---|---|
| Группа | До 200 | Закрытая; права участников, администраторы, теги участников |
| Супергруппа | Интерфейсом не ограничено; практический предел задаёт fan-out | Дополнительно: публичная ссылка, заявки на вступление, тег сервера, медленный режим, скрытие списка участников, журнал действий |
| Канал | Интерфейсом не ограничено | Публикация только администраторами, подпись авторов |

Владелец может преобразовать группу в супергруппу и обратно. При обратном преобразовании функции супергруппы отключаются, а их настройки сохраняются.

**Роли супергрупп** устроены по образцу Discord: упорядоченный список ролей, последняя — `@everyone`. Права участника — объединение прав его ролей; право «Администратор» включает все. В комнате действуют переопределения: сначала запреты и разрешения `@everyone`, затем объединённые запреты и разрешения ролей участника. Управлять можно только ролями ниже собственной наивысшей и выдавать только имеющиеся права. Получатель снимка проверяет те же условия (`role_change_ok` в `state.rs`), поэтому изменённый клиент не может присвоить себе права.

## 8. Учётные записи и аутентификация

### 8.1. Аутентификация устройства

1. `POST /v1/auth/challenge` — ретранслятор выдаёт nonce (24 байта, срок действия 60 с).
2. `POST /v1/auth/verify` — клиент возвращает подпись Ed25519 над nonce.
3. Ретранслятор выдаёт токен `dh_pub ‖ expires_at ‖ HMAC-SHA256(server_key, …)` сроком 1 ч. Токен проверяется без хранения состояния.

### 8.2. Регистрация имени и пароль

Имя пользователя (`@имя`: 3–32 символа `a–z0–9_.`) регистрируется после подтверждения адреса электронной почты. Код подтверждения действует 10 минут, регистрационный тикет — 30 минут.

Пароль на ретранслятор не передаётся. Клиент передаёт производный секрет:

```
auth_secret = "aqv2$" ‖ hex(Argon2id(password,
                                     salt = SHA-256("aquamarine/auth/v1|" ‖ lower(email))[0..16],
                                     m = 19 МиБ, t = 2, p = 1))
```

Ретранслятор хранит PBKDF2-HMAC-SHA256(auth_secret; 120 000 итераций; случайная соль 16 байт).

- Учётные записи, созданные до введения `auth_secret`, проходят вход по прежней схеме и автоматически переводятся на новую.
- Без настроенного SMTP ретранслятор работает в режиме разработки: коды выводятся в консоль и в панель администратора.

### 8.3. Несколько устройств

Учётная запись работает одновременно на нескольких устройствах (до 11: основное и 10 дополнительных). У каждого устройства собственный ключ идентичности, собственные предварительные ключи и собственные сеансы Double Ratchet; закрытые ключи между устройствами не передаются.

| Элемент | Устройство |
|---|---|
| Добавление | Вход на новом устройстве по подтверждённому адресу и паролю (`POST /v1/users/login`): ключ устройства добавляется к учётной записи, прежние устройства остаются в сети |
| Адрес на ретрансляторе | Основное устройство — `имя`, дополнительное — `имя~<id>`, где `id` — первые 6 байт ключа DH в hex. Конверты, пакеты ключей и очередь входящих ведутся по адресу |
| Список устройств | `GET /v1/devices/:имя` (публичный, как пакеты ключей); `GET /v1/me/devices`; `POST`/`DELETE /v1/me/devices/:id` — переименование и выход |
| Отправка | Клиент шифрует сообщение отдельно для каждого устройства собеседника и отдельно для каждого своего устройства (копия в обёртке `[sync:v1]`), поэтому отправленное видно на всех устройствах отправителя |
| Приём | Сеанс выбирается по адресу устройства отправителя, чат — по имени учётной записи |
| Отключение | Устройство отключается с любого другого. Отключение основного делает основным устройство, с которого выполнено действие |
| Репликация | Список устройств хранится в строке учётной записи и реплицируется федерацией вместе с ней |
| Совместимость | Клиенты прежних версий видят только основное устройство собеседника; ретрансляторы прежних версий отвечают 404 на `/v1/devices`, и клиент отправляет по имени, как раньше |

Звонок приходит на все устройства собеседника; когда одно из них отвечает или отклоняет вызов, остальные прекращают вызов.

## 9. Резервное копирование и перенос учётной записи

### 9.1. Назначение

Зашифрованная резервная копия решает две задачи:

- переносит на новое устройство историю, группы, контакты и настройки;
- восстанавливает учётную запись, если все устройства утрачены.

Ключ идентичности и сеансы из копии на новое устройство не переносятся: устройство сохраняет собственные ключи и входит как ещё одно устройство учётной записи (п. 8.3).

Ретранслятор хранит копию, но расшифровать её не может.

### 9.2. Формат `AQBK1`

```
"AQBK1" ‖ u32 BE длина_заголовка ‖ заголовок (JSON) ‖ nonce[12] ‖ ChaCha20-Poly1305(DEK, nonce, AAD = "AQBK1", DEFLATE(payload))
```

| Поле заголовка | Содержимое |
|---|---|
| `kdf` | Параметры Argon2id: соль 16 байт, m = 64 МиБ, t = 3, p = 1. Хранятся в заголовке, чтобы их можно было усилить позже |
| `pw` | DEK, обёрнутый ключом Argon2id(пароль) |
| `rk` | DEK, обёрнутый ключом HKDF-SHA256(энтропия ключа восстановления, info = `aquamarine backup recovery v1`) |
| `created` | Время создания, секунды Unix |

Ключи:

- **DEK** — случайный 256-битный ключ данных.
- **Ключ восстановления** — 256 бит энтропии. Пользователь получает его однократно в виде 24 слов словаря BIP-39.

Копию открывает любой из двух ключей: пароль учётной записи или ключ восстановления. Ключ входа (п. 8.2) и ключ копии вычисляются с разными солями и параметрами. Поэтому знание `auth_secret` не позволяет вычислить ключ копии.

### 9.3. Содержимое и периодичность

| Параметр | Значение |
|---|---|
| Входит в копию | Записи хранилища (идентичность, сеансы, SPK, OPK, история, группы, токены ботов) и настройки интерфейса |
| Не входит в копию | Медиафайлы и локальный медиакэш |
| Предельный размер | 64 МиБ |
| Периодичность | Через ≈ 20 с после важного изменения (группы, контакты, профиль, настройки, папки, закрепления, приватность) — не чаще раза в 2 мин; после новых сообщений — не чаще раза в 20 мин; не реже раза в 6 ч; при закрытии приложения, если были изменения; по команде пользователя |
| Включение | По умолчанию при регистрации и входе по паролю; отключается в настройках |
| Эндпоинты | `PUT`, `GET`, `DELETE /v1/backup`; `POST /v1/backup/fetch` (по тикету подтверждённого адреса и `auth_secret`) |

### 9.4. Процедура переноса

1. На новом устройстве пользователь подтверждает адрес электронной почты и вводит пароль.
2. Клиент загружает копию и расшифровывает её паролем. Если пароль изменён или утрачен, используется ключ восстановления.
3. Записи хранилища импортируются, кроме ключа идентичности, предварительных ключей и сеансов этого устройства, и состояние клиента перестраивается. Ключ устройства добавляется к учётной записи (п. 8.3).

Если ретранслятор недоступен, клиент выполняет те же действия через другой узел федерации: копии реплицируются (раздел 11).

## 10. Хранение данных на устройстве

### 10.1. Расположение

| ОС | Каталог данных |
|---|---|
| Linux | `~/.local/share/app.aquamarine.desktop` |
| Windows | `%APPDATA%\app.aquamarine.desktop` |
| macOS | `~/Library/Application Support/app.aquamarine.desktop` |

Каталог переопределяется переменной `AQUA_DATA_DIR`.

### 10.2. Состав и защита

| Данные | Место хранения | Защита |
|---|---|---|
| Идентичность, сеансы, предварительные ключи | `vault.sqlite`: каждая запись зашифрована ChaCha20-Poly1305; AAD = `Aquamarine/Vault/v1:` ‖ ключ записи | Шифрование |
| История личных и групповых чатов, «Избранное» | Записи хранилища `hist:<id>`: JSON → DEFLATE → ChaCha20-Poly1305 | Шифрование |
| Состояние групп | Запись хранилища `groups` | Шифрование |
| Токены собственных ботов | Записи хранилища `bot_token:<имя>` | Шифрование |
| Ключи резервной копии, ключ восстановления | Записи хранилища `backup:*` | Шифрование |
| Мастер-ключ хранилища (256 бит) | Системное хранилище ключей; при его отсутствии — файл `master.key` | Средствами ОС |
| Настройки интерфейса, папки, закрепления | Хранилище WebView (localStorage) | Нет |
| Медиакэш, стикеры, звуки | `media-cache/`, `stickers/`, `sounds/` | Нет |

### 10.3. Запись истории

Фоновый процесс раз в 3 с записывает изменившиеся чаты; изменения определяются сравнением хешей. При завершении приложения запись выполняется принудительно. Файлы `saved-messages.json` и `groups.json` прежних версий переносятся в хранилище и удаляются.

### 10.4. Удаление сообщений

- «Удалить у себя» удаляет сообщение только на данном устройстве.
- «Удалить у всех» отправляет собеседникам служебное сообщение E2EE. В группах эта операция доступна также модераторам.
- Параметр «Сохранять удалённые» (по умолчанию включён) оставляет у получателя удалённое собеседником сообщение с пометкой. Предыдущие версии отредактированных сообщений сохраняются аналогично.
- Вложения и статьи удаляются только локально.

## 11. Федерация ретрансляторов

Несколько ретрансляторов образуют единую сеть. Узлы используют:

- общий секрет (`AQUA_FED_SECRET` или панель администратора);
- перечень адресов друг друга (`AQUA_FED_PEERS`).

Каждый межсерверный запрос подписывается заголовком:

```
x-aqua-fed: <unix_ms>.<hex HMAC-SHA256(secret, METHOD "\n" PATH "\n" unix_ms "\n" hex(SHA-256(body)))>
```

Допустимое расхождение часов — ±5 минут.

| Функция | Механизм |
|---|---|
| Уведомление об изменении | Узел раз в 1,5 с сравнивает отметку изменений (наибольшие `updated_at` таблиц `users` и `backups`). Если она сдвинулась, узел отправляет соседям подписанный `POST /v1/fed/poke`, и они немедленно выполняют выборку. Без уведомлений выборка выполняется каждые 30 с |
| Репликация учётных записей | Узлы забирают у соседей строки `users` с `updated_at` больше курсора (страницами по 500); при конфликте побеждает более поздняя запись. Учётные записи ботов не реплицируются |
| Репликация медиа профилей | Если у принятой строки изменилась версия аватара, баннера или трека, узел сразу копирует файл у соседа (`/v1/fed/media/:user/:kind`) и хранит его у себя |
| Репликация резервных копий | Тем же способом, по `updated_at` |
| Доставка | Конверт пересылается узлу, к которому подключён получатель (`POST /v1/fed/deliver`). Если получатель не в сети ни на одном узле, конверт ждёт на исходном узле; узел, к которому получатель подключится, забирает его (`/v1/fed/inbox/:user`) |
| Ключи, файлы | При локальном отсутствии запрашиваются у соседей; целостность файлов проверяется по CID. Одноразовые ключи (OPK) не реплицируются, чтобы один ключ не был выдан дважды |
| Отказоустойчивость клиента | `GET /v1/fed/peers` возвращает публичные адреса узлов. Клиент хранит до 12 адресов и при недоступности текущего узла переподключается к следующему |

Протокол проверяется интеграционными тестами `crates/aqua-server/tests/federation.rs`: два узла в одном процессе; тест `changes_are_pushed_to_peers` проверяет, что учётная запись, аватар и резервная копия доходят до второго узла без ручной синхронизации, а ключи переживают перезапуск.

## 12. Боты

Бот — учётная запись, которой управляет внешняя программа через HTTP API (`/v1/bot/*`). Переписка с ботом **не защищена сквозным шифрованием**; клиент указывает на это в каждом таком чате.

Меры безопасности:

- на сервере хранится только SHA-256 токена (192 бита энтропии);
- токен передаётся в заголовке `Authorization: Bot …`;
- бот может писать только пользователям, которые писали ему, и владельцу; команда `/stop` отзывает разрешение;
- частота отправки ограничена: 30 сообщений/с на бота, 1 сообщение/с на чат;
- длина текста — до 4096 символов;
- у одного владельца — не более 20 ботов.

Полное описание API, ограничений и модели безопасности — в [docs/BOTS.md](docs/BOTS.md). Примеры: [`bots/echo_bot.py`](bots/echo_bot.py), [`tools/aqua-console.py`](tools/aqua-console.py).

**Совместимость с Telegram Bot API.** Ретранслятор принимает запросы `/bot<токен>/<метод>` в формате Telegram, поэтому бот, написанный для Telegram (python-telegram-bot, aiogram, telegraf, grammY, pyTelegramBotAPI), работает без изменений: библиотеке указывается адрес ретранслятора вместо `api.telegram.org` и токен в виде `<число>:<токен>` (кнопка «Токен Telegram» в настройках ботов). Поддерживаются `getMe`, `getUpdates`, вебхуки с `secret_token`, `sendMessage` с `parse_mode` и встроенные клавиатуры: кнопки выводятся нумерованным списком, ответ пользователя номером превращается в `callback_query`. Подробности — в [docs/BOTS.md](docs/BOTS.md#9-совместимость-с-telegram-bot-api).

Библиотека для ботов на Python — [`sdk/python`](sdk/python) (`aquabot`). Она подключает нейросети (llama.cpp, Ollama, OpenAI-совместимые серверы, Anthropic), содержит встроенную математику и команду `aquabot run` для готового ИИ-бота.

## 13. Наборы стикеров и эмодзи

Наборы Telegram импортирует **ретранслятор** через Telegram Bot API (`getStickerSet`):

- токен бота Telegram задаёт администратор ретранслятора;
- пользователь передаёт только ссылку `t.me/addstickers/…` или `t.me/addemoji/…`;
- ограничения импорта: до 200 элементов, до 2 МиБ на файл, 8 параллельных загрузок;
- импортированный набор хранится в `aqua-packs/` и раздаётся всем клиентам ретранслятора.

Поддерживаемые форматы: WebP, WebM (VP9), TGS (Lottie). TGS воспроизводится библиотекой lottie-web. Собственные стикеры пользователя создаются во встроенном редакторе и хранятся локально.

## 16. Известные ограничения

1. Независимый аудит кода и протокола не проводился.
2. Протокол несовместим с Signal и Matrix.
3. Активный оператор ретранслятора может подменить ключи при первом контакте. Для обнаружения подмены нужна ручная сверка отпечатка.
4. Метаданные (кто, кому, когда, сколько) доступны оператору ретранслятора.
5. Каждое устройство учётной записи имеет свой ключ; собеседник видит их как отдельные ключи (сверка отпечатка — по каждому устройству). История, накопленная до добавления устройства, приходит на него из резервной копии, а не по сети между устройствами. Реакции, отметки о прочтении и голоса в опросах между своими устройствами не синхронизируются.
6. Групповые сообщения рассылаются попарно; стоимость отправки растёт линейно с числом участников.
7. Очередь входящих сообщений ботов хранится в памяти и теряется при перезапуске ретранслятора.
8. Резервная копия защищена паролем учётной записи (Argon2id, 64 МиБ) или ключом восстановления. Оператор ретранслятора может перебирать слабые пароли офлайн; рекомендуется пароль не короче 12 символов.
9. Медиакэш и настройки интерфейса хранятся на устройстве без шифрования.
10. Шрифты интерфейса загружаются с Google Fonts.
11. Сборка для iOS не подписана и устанавливается только через AltStore или SideStore.
12. В Wayland значок окна определяется файлом `.desktop`. Смена значка приложения во время работы отражается в заголовке и интерфейсе, но не на панели задач.

## 18. Развёртывание ретранслятора

```bash
AQUA_LISTEN=0.0.0.0:7777 ./aqua-server-linux-x64
```

Для схем `https://` и `wss://` перед ретранслятором устанавливается обратный прокси с TLS (Caddy, nginx).

Панель администратора (`/admin`, доступ по токену) содержит:

- статистику;
- режим «только по приглашению»;
- настройку SMTP;
- токен Telegram;
- параметры федерации.

## 19. Сборка и тестирование

### 19.1. Требования

- Rust stable;
- Node.js 22 или новее;
- Tauri CLI 2 (`cargo install tauri-cli --version '^2'`);
- для Linux — WebKitGTK 4.1 и GTK 3.

### 19.2. Сборка

```bash
sudo pacman -S --needed rustup nodejs npm base-devel webkit2gtk-4.1 libappindicator-gtk3 librsvg patchelf   # Arch Linux
sudo apt install libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev patchelf                                   # Debian, Ubuntu

./build-all.sh                                   # все компоненты → ../Aquamarine-apps (в Windows: build-all.bat)
cargo build --release -p aqua-server             # только ретранслятор
cd crates/aqua-client-ui/ui && npm ci && npm run build && cd .. && cargo tauri build   # только клиент
```

### 19.3. Тестирование

```bash
cargo test                                        # aqua-core, aqua-client-core, aqua-server (включая e2e и федерацию)
cd crates/aqua-client-ui && cargo test            # клиент: история, медиа, наборы, активность
python3 ../../tools/check-invokes.py              # соответствие вызовов IPC командам Rust
(cd ui && npx svelte-check)                       # проверка типов интерфейса
tools/e2e/run.sh                                  # реальный клиент Linux под Xvfb
```
