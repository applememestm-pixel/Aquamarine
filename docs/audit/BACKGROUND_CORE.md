# Ядро без окна на Android — план (C, 27.11)

Только план. В коде пока ничего не сделано.

## Как сейчас

- Ядро мессенджера (Rust) запускается вместе с окном. `MainActivity` → Tauri → `lib.rs::run()` → `setup` → `AppState`, подключение (`commands.rs::connect_to_server`), приём (`handle_incoming`).
- Логика приёма завязана на `AppHandle`: в `commands.rs` — 71 упоминание. Через него идут состояние, события в UI, плагины.
- Без окна ядра нет. «Оставаться на связи» (`AquaSyncService`) только не даёт убить уже запущенный процесс. Сигнал UnifiedPush (`AquaPushReceiver`) при убитом процессе поднимает процесс, но не ядро: сейчас он показывает «Новое сообщение», а сообщения придут, когда откроют приложение.

## Что нужно

По сигналу «проснись» — подключиться, забрать очередь, расшифровать, записать историю и показать уведомление с выбранным предпросмотром. Всё это без окна, а когда окно откроется — без второго ядра.

## Варианты

| Вариант | Суть | Оценка |
|---|---|---|
| A. Ядро как библиотека для службы | Приём отделён от Tauri: свой тип `Core` вместо `AppHandle`, вход через JNI (`AquaCore.start`). Служба или задача по сигналу вызывает его. Окно, открываясь, берёт тот же `Core`. | **Рекомендую.** Большой рефакторинг, но правильная граница. |
| B. Tauri без видимого окна из службы | Tauri на Android требует `Activity`. | Не поддерживается. |
| C. Держать процесс всегда (как сейчас) | Служба переднего плана. | Есть, но тратит батарею и всё равно убивается некоторыми прошивками. |

## План для A — по шагам, каждый со своими тестами

1. **Граница.** Вынести из `commands.rs` приём сообщения (`handle_incoming` и то, что он трогает: сессии, `multidev`, `history`, `bgnotify`) за типаж `Host`: события в UI, уведомление, плагины. Две реализации: Tauri (окно) и «без окна» (только уведомление и запись). Поведение не меняется. Тесты приёма — на реализации «без окна».
2. **Один владелец.** Служба и окно — один процесс, поэтому одно ядро на процесс (`static`). Окно при старте подключается к уже работающему ядру, а не создаёт второе: два ядра разошлись бы в состоянии ratchet. Плюс файловая блокировка хранилища на случай второго процесса.
3. **Ключ хранилища без окна.** Уже возможно: `vault_key::resolve` и `AquaKeystore` не требуют `Activity`. Проверить на телефоне после перезагрузки (AQUA-SEC-013), пока экран заблокирован: ключ Keystore может быть недоступен до первой разблокировки. Тогда — только «Новое сообщение», расшифровка позже.
4. **Запуск по сигналу.** Android 12+ не даёт запускать службу переднего плана из фона по сигналу UnifiedPush (исключение только для FCM высокого приоритета). Поэтому — срочная задача `JobScheduler` (expedited) или `WorkManager`: несколько минут работы, затем ядро отключается. Без отключения от батарейной оптимизации — проверить на Xiaomi, Huawei, Samsung.
5. **JNI.** `AquaCore.wake(dataDir)` из задачи. Rust загружается без Tauri (`System.loadLibrary`). Логи и сбои — в `crashreport`.
6. **Уведомление.** Предпросмотр — из `bgnotify::Prefs`, которые UI уже сохраняет. Запертые чаты и блокировка приложения — как сейчас.
7. **Проверка.** Эмулятор в CI: убить процесс, отправить сигнал, ждать запись в историю. Затем физические телефоны.

## Риски

- Два ядра одновременно → расхождение сессий и потерянные сообщения. Главный риск, его закрывает шаг 2.
- Keystore до первой разблокировки (шаг 3).
- Лимиты фоновой работы у производителей (шаг 4).
- Объём: шаг 1 затрагивает большую часть `commands.rs`, это отдельный PR.
